# Order-create processing

Implemented for issue #9. The [verified checkpoint](s1-processing-checkpoint.md) records native MySQL, Docker, and twenty graceful worker restart checks; forced-crash acceptance remains pending.

Active Job uses the already-locked Solid Queue 1.7.0 adapter. Its tables share the primary MySQL database, using the gem's default inherited connection. Queue insertion happens only after the receipt adapter returns from its committed transaction. Sharing a database does not make receipt and enqueue atomic. A failed enqueue retains a pending event; Solid Queue's recurring scheduler requests a bounded recovery scan every minute.

`ruby bin/jobs` starts the standard Solid Queue supervisor, dispatcher, worker, and recurring scheduler. `ruby bin/jobs check` validates its configuration. Docker Compose starts the jobs service after the application's migrations and health check. No custom queue, Redis, separate business database, or external merchant call is introduced.

The queue migration derives from the install template in the checksum-verified `solid_queue-1.7.0.gem` already pinned by `Gemfile.lock` (SHA-256 `6566b70b801d1c317c81bba7bcdd5677c019afac584a30374b4164002ca356d3`). It is wrapped as a normal application migration and omits destructive `force: :cascade` creation. The [upstream MIT notice](licenses/solid-queue-MIT.txt) is retained. Queue configuration follows that pinned gem's templates, not a separately upgraded queue implementation.

EventLedger claims an eligible canonical event under a row lock, records an attempt and a SHA-256 lease-token digest, and commits before calling Orders. The random token exists only in the executing claim object; raw tokens are absent from database SQL diagnostics. An upgrade migration hashes existing claim values before renaming their columns and cannot recover plaintext on downgrade. Claims last 300 seconds. A current unexpired claim prevents concurrent dispatch; an expired claim can be replaced. Only the current token may acknowledge the lifecycle state. The queue payload contains internal shop/event IDs, not a webhook body or secret.

Orders locks the tenant/source/order projection and checks the unique `(event_id, handler_name, handler_version)` effect. Projection updates and effect insertion share one primary MySQL transaction. An enclosing transaction is rejected. Composite foreign keys bind event and projection associations to the tenant. A duplicate returns the original effect outcome without another projection transition. Deadlocks retry the entire effect transaction, with at most five attempts.

For the current order-create topic, an older or equal source timestamp records a `stale` effect and leaves the projection unchanged. A strictly newer timestamp updates its source position and transition counter. Comparison retains all nine fractional digits; arrival order and event ID are not tie-breakers. Later topics must extend the domain policy explicitly.

After the effect commits, EventLedger records success separately. Handler failures record only the fixed `handler_failed` code, schedule another eligible attempt after 2/4/8/16 seconds, and reach `dead_letter` on the fifth failure. Expired fifth claims also become dead letter after their abandonment is recorded. A recovery scan selects at most 100 eligible pending/retry events or expired claims; duplicate enqueues are permitted. Dead letters are excluded from automatic recovery. Operator replay is not implemented by this increment.

MySQL tests cover atomic effect rollback, duplicate effects, tenant foreign keys, timestamp ordering, lease ownership, bounded failure state, and the receipt/enqueue gap. Docker CI sends ten signed deliveries and waits for a real worker to reach one event, one effect, and one projection transition. A clock-advanced unacknowledged-effect test is not a real process-kill experiment; full crash/restart, 100-delivery concurrency, repeated failure stability, replay, observability, and benchmark acceptance remain separate required gates.
